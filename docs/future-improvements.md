# 项目后续改进方向

本文根据当前 nano-pi 源码、测试和教学网站整理后续可改进事项。项目的目标是从零讲清 coding agent 的核心数据流，因此下面的方向分成两类：一类增强教学内容和维护体验，另一类让 nano-pi 更接近可日常使用的工具。实现时可以按需要选择，不必一次性全部完成。

## 现状与原则

目前项目已经具备 Agent Loop、OpenAI 兼容流式调用、四个文件/命令工具、会话 JSONL 持久化、上下文压缩、单元测试及离线 Trace 教学网站。源码注释也明确记录了一些教学版简化，例如工具参数不校验、工具串行执行、按消息条数压缩，以及工具默认可访问启动进程能够访问的文件和命令。

后续改进建议遵循以下原则：

1. **先补边界，再扩展功能。** 优先明确文件访问、命令执行、错误恢复等行为，再增加新工具和界面功能。
2. **教学版与产品化能力分层。** 如参数校验和路径限制可以先作为“生产环境需要补充什么”的讲解，再决定是否进入默认实现。
3. **每个改动有可验证结果。** 核心行为通过自动化测试覆盖；教学网站的内容和代码切片使用现有检查流程验证。

## 优先级一：适合近期完成

### 1. 明确并收紧工具的文件访问范围

**当前情况：** `src/tools.ts` 的文件工具直接使用传入路径，`run_bash` 也以进程工作目录执行命令。工具目前没有项目根目录边界，也没有对路径或命令做授权确认。

**建议改进：**

- 以启动目录作为可配置的工作区根路径；对文件工具解析绝对路径并检查其是否仍位于工作区内，处理 `..`、绝对路径和符号链接等情况。
- 为工作区外访问设计明确策略，例如拒绝、显式允许目录或交互确认，不要只靠字符串前缀判断路径归属。
- 为有副作用的工具提供可选的确认钩子或只读模式；界面展示即将写入的文件路径或执行的命令。
- 将这一边界及教学版本的默认行为写入新手指南，避免使用者误以为工具只影响项目目录。

**完成标准：** 对工作区内路径正常读写；路径穿越、工作区外路径及符号链接逃逸按策略被拒绝或确认；相关行为有测试覆盖。

### 2. 校验模型返回的工具参数

**当前情况：** 工具定义包含 JSON Schema，但 `src/agent.ts` 收到参数后直接交给 `execute`。`src/llm.ts` 对无法解析的参数 JSON 会回退为空对象。

**建议改进：**

- 在调用 `execute` 前校验参数类型、必需字段和字段格式；无效参数应转为工具错误结果并写回 Context，而不是让异常逃逸或静默变成空对象。
- 区分“参数 JSON 格式错误”和“工具执行失败”，以便日志和模型获得准确反馈。
- 如果暂不引入 Schema 校验依赖，可先实现当前四个工具所需的轻量校验，并在文档中注明范围。

**完成标准：** 缺少必需参数、参数类型错误和非法 JSON 都不会触发文件或命令副作用；模型可以收到明确错误并继续对话。

### 3. 改进 LLM 流式协议的异常处理

**当前情况：** `src/llm.ts` 已处理分片 SSE 和请求中断，但网络流结束后尚未处理缓冲区中未换行的最后一行；工具参数解析失败时会按 `{}` 继续。部分请求或响应错误主要以通用错误事件呈现。

**建议改进：**

- 处理流结束时残留的 SSE 数据，并覆盖 CRLF、分块 UTF-8 字符、空行及格式不完整数据等情况。
- 对缺少工具名、无效参数 JSON、工具调用索引异常等数据给出可追踪的协议错误，而非伪造可执行的参数。
- 在错误信息中保留 HTTP 状态码和服务端错误正文，同时避免输出 API Key 等凭证。
- 评估网络超时和有限次数重试；只对可安全重试的请求启用，避免重复执行工具或重复计费。

**完成标准：** 使用模拟 ReadableStream 覆盖正常、截断和畸形响应；错误可被上层稳定处理；凭证不会出现在错误输出中。

### 4. 增加 Agent Loop 的终止与恢复策略

**当前情况：** `src/agent.ts` 的循环没有最大步数限制，注释说明这是教学取舍。工具串行执行；`AbortSignal` 可以中断模型请求和命令执行。

**建议改进：**

- 提供可选的最大模型轮数或最大工具调用数，达到上限时给出清晰的 `turn_end` 原因。
- 记录每轮模型请求和工具执行的耗时，帮助识别长时间运行或反复调用同一工具的情况。
- 保持中断后的 `tool_use` / `tool_result` 配对完整，并为生成器异常、工具超时和用户中断分别定义行为。
- 如增加并行工具调用，先明确工具间副作用和结果顺序，再考虑并发；不要仅为了速度改变现有可预测性。

**完成标准：** 循环达到限制后能正常结束并持久化有效消息；中断、超时和工具异常均不会留下未配对的工具调用。

## 优先级二：提升日常使用体验

### 5. 让会话可管理、可恢复

**当前情况：** `src/cli.ts` 将消息追加到用户目录下同一个 `~/.nanopi/session.jsonl`，所有项目共享会话；加载时会跳过损坏行，持久化按进程内消息计数追加并校验尾部对齐（compaction 使下标失效时整体重写文件）。

**建议改进：**

- 按项目目录区分会话，或提供会话名称和文件路径配置，避免不同项目的上下文混用。
- 增加新建/清空/导出会话等基本管理入口，并支持会话文件备份或轮转。
- 为 JSONL 记录增加版本字段或迁移策略，未来调整消息结构时仍可读取旧会话。
- 评估异常退出时的写入完整性；可采用单次批量追加或临时文件加原子替换等方案，并保留损坏行诊断信息。

**完成标准：** 可以明确选择或重置会话；不同项目可独立保存；格式升级和损坏记录有可理解的恢复提示。

### 6. 改善上下文预算管理

**当前情况：** Agent 在消息条数达到阈值时调用模型总结旧消息，保留近期消息；这比按 token 管理更简单，但单条消息可能很长，实际上下文仍可能超出模型限制。

**建议改进：**

- 支持按模型上下文窗口和估算 token 数触发压缩，并让预算可配置。
- 为工具结果设置大小限制或按工具类型采用不同截断策略；提供继续读取被截断内容的方式。
- 记录压缩前后的消息数、估算 token 和摘要失败原因，便于排查上下文溢出。
- 保留已有的轮次边界规则，并为压缩失败、被中断以及工具调用配对写测试。

**完成标准：** 超长单条消息也能触发预算控制；压缩不会拆散工具调用和结果；摘要失败时保留原上下文。

### 7. 改进终端可用性和跨平台验证

**当前情况：** TUI 使用 Node.js `readline` 实现单行输入，`run_bash` 调用系统默认 shell；项目文档记录了 Windows 上教学网站开发命令的特别处理。

**建议改进：**

- 将输入、忙碌、错误和中断状态的反馈做得更明确，例如显示运行状态、耗时和取消结果。
- 为空输入、EOF、连续中断、管道输入和任务运行期间关闭输入流增加端到端覆盖。
- 在 CI 中分别验证 Windows 与 Linux/macOS 的构建和核心测试，检查 shell 差异及路径处理。
- 为 `run_bash` 的名称与系统默认 shell 行为提供更明确的命名或提示。

**完成标准：** 常见输入结束和中断场景表现一致；核心测试在 Windows 和类 Unix 环境中通过；文档中的命令可按平台直接使用。

## 优先级三：增强教学与项目维护

### 8. 降低教学网站对源码行号的依赖

**当前情况：** `web/app/lesson-data.ts` 通过行号切片展示渐进源码，`npm run check:slices` 用来发现偏移。架构文档也说明 Trace 行号来自生成快照，源码变化后需要重新生成。

**建议改进：**

- 逐步将硬编码行区间替换为带稳定标记的源码片段，或根据函数/注释标记定位片段。
- 将源码快照检查、切片检查和 Trace 更新状态纳入统一维护说明或自动化检查。
- 对缺少 `docs/pi-from-scratch.md` 的克隆场景，提供清晰提示和验证步骤，避免使用者不确定生成内容来自哪里。
- 对文章、代码片段和 Trace 建立可追溯的版本信息，帮助确认教学内容对应的源码版本。

**完成标准：** 常规源码增删行不会静默展示错误片段；内容缺失或 Trace 过期时能由检查命令发现并给出定位信息。

### 9. 扩充测试矩阵与自动化检查

**当前情况：** 根目录已有 Vitest 测试，覆盖 LLM 消息转换、SSE 基本解析、Agent 执行和工具行为；网站有独立的构建测试与 lint 命令。根目录尚未定义统一的 lint 或 CI 脚本。

**建议改进：**

- 补齐 SSE 中断/异常、参数解析失败、HTTP 错误、上下文压缩边界、会话损坏行和工具中断等关键路径测试。
- 为 `src/tools.ts` 使用临时目录测试文件访问与截断；为会话测试使用独立临时文件，避免依赖用户主目录状态。
- 在 CI 中运行根目录 `npm test`、`npm run build`、`npm run check:slices`，并运行网站 lint、测试或构建。
- 将真实 API 测试与默认 CI 隔离，避免普通测试依赖密钥、外网或产生额外费用。

**完成标准：** 拉取请求可自动验证核心源码和教学网站；关键异常路径有稳定的离线测试；真实 API 测试仅在显式配置时运行。

### 10. 补充配置与诊断能力

**当前情况：** API Key、模型和接口地址通过环境变量读取；模型请求默认没有单独的超时配置，错误主要打印到终端。

**建议改进：**

- 将模型名、接口地址、最大输出 token、请求超时和会话位置集中为可文档化的配置项。
- 启动时验证必要配置，并对可疑的 URL、空模型名等情况提供及时错误提示。
- 增加可选的结构化诊断日志，包含请求耗时、工具名和错误类型，不记录密钥及不必要的对话正文。
- 在新手指南中补充日志位置、配置优先级和常见错误排查流程。

**完成标准：** 配置项有默认值、校验规则和示例；故障诊断不需要临时修改源码，也不会意外记录凭证。

## 推荐实施顺序

1. **先处理工具安全边界和参数校验**，因为它们影响文件写入与命令执行的边界。
2. **补齐协议及 Agent 异常路径测试**，让后续可靠性改动有稳定保障。
3. **增加会话管理和模型上下文预算**，提升长时间使用的体验。
4. **完善 CI 与跨平台验证**，减少源码和教学网站之间的维护回归。
5. **按需要演进教学网站切片机制及界面体验**，保留项目“从零理解 Agent”的核心定位。
